Which EC2 Instances and OS Support EFA OS-Bypass via Libfabric?

Amazon EC2 Elastic Fabric Adapter (EFA) provides OS-bypass capabilities through the Libfabric communications library across high-performance Linux operating systems and numerous compute-optimized, memory-optimized, accelerated computing, and general-purpose EC2 instance families. By routing packets directly from user-space applications to the custom-built Nitro network hardware, EFA eliminates kernel context-switching overhead, significantly reducing network latency and maximizing throughput for tightly coupled High Performance Computing (HPC) and distributed Machine Learning (ML) workloads. This article details the architecture of EFA OS-bypass via Libfabric, lists the supported Amazon EC2 instance families, outlines compatible operating systems, and explains how the software stack enables low-latency communication at scale.

How EFA OS-Bypass and Libfabric Work Together

Traditional TCP/IP networking requires applications to invoke system calls that transition execution from user space to the operating system kernel. The kernel processes network headers, manages socket buffers, and handles interrupts before passing data to the network interface card (NIC). While reliable for general-purpose workloads, this path introduces microsecond-level latency jitter and consumes CPU cycles that could otherwise be dedicated to computation.

Elastic Fabric Adapter overcomes this bottleneck using an architecture known as OS-bypass. Through the OpenFabrics Interfaces (OFI) Libfabric API, user-space libraries communicate directly with the EFA hardware queues managed by the AWS Nitro System:

  1. User-Space Queue Management: When an application initializes communication via MPI (such as Open MPI or Intel MPI) or collective communication libraries (such as AWS OFI NCCL for PyTorch and TensorFlow), Libfabric allocates send, receive, and completion queues directly in user-space memory.
  2. Direct Memory Access (DMA) and RDMA: The EFA provider (ofi_efa) within Libfabric registers memory regions with the EFA device. Data transfers occur via DMA and Remote Direct Memory Access (RDMA) read/write operations without copying buffers through the OS kernel.
  3. Scalable Reliable Datagram (SRD): EFA relies on the AWS-engineered Scalable Reliable Datagram (SRD) protocol in the Nitro hardware. Unlike traditional InfiniBand, which struggles with congestion over Equal-Cost Multi-Path (ECMP) routing, SRD sprays packets across multiple network paths simultaneously and handles out-of-order delivery and retransmissions directly in hardware.

The effective latency \(L_{\text{total}}\) in an OS-bypass model eliminates the kernel traversal time \(T_{\text{kernel}}\), leaving only the user-space library serialization \(T_{\text{lib}}\), PCIe traversal \(T_{\text{PCIe}}\), and physical network propagation \(T_{\text{fabric}}\):

\[L_{\text{total}} = T_{\text{lib}} + 2 \cdot T_{\text{PCIe}} + T_{\text{fabric}}\]

Supported Operating Systems for EFA OS-Bypass

Note that while all current-generation EC2 instances support the ENA (Elastic Network Adapter) driver for standard TCP/IP networking across almost any OS, OS-bypass via Libfabric on EFA requires specific operating system kernel drivers (efa.ko via rdma-core) and user-space libraries packaged in the official AWS EFA installer.

Supported Linux Distributions

AWS provides full OS-bypass support via the EFA installer on the following 64-bit (x86_64 and arm64 Graviton) Linux operating systems:

  • Amazon Linux: Amazon Linux 2023 (AL2023) and Amazon Linux 2 (AL2)
  • Ubuntu: Ubuntu 20.04 LTS, Ubuntu 22.04 LTS, and Ubuntu 24.04 LTS
  • Red Hat Enterprise Linux (RHEL): RHEL 8 and RHEL 9 (and compatible derivatives)
  • Rocky Linux: Rocky Linux 8 and Rocky Linux 9
  • AlmaLinux: AlmaLinux 8 and AlmaLinux 9
  • SUSE Linux Enterprise Server (SLES): SLES 15 (SP4 and later recommended for modern HPC stacks)
  • CentOS: CentOS 7 and CentOS Stream 8/9 (legacy support in earlier EFA installer releases)

Windows Server Support Limitations

While EFA devices can be attached to certain Windows Server instances for standard IP networking, OS-bypass via Libfabric is not supported on Windows operating systems. Distributed workloads requiring EFA OS-bypass and SRD capabilities must run on one of the supported Linux distributions listed above, either natively on the host or inside privileged Linux containers (such as Docker, Singularity/Apptainer, or AWS Batch/EKS pods with /dev/infiniband/uverbs* device pass-through).

Verifying EFA OS-Bypass Support and Configuration

Once an EFA-enabled EC2 instance is launched with a supported Linux OS and an EFA network interface attached, you can verify that the kernel module, rdma-core user-space libraries, and Libfabric EFA provider are operational.

Checking the Libfabric EFA Provider

Run the fi_info utility included with the AWS EFA installer to query the active EFA Libfabric providers:

fi_info -p efa

A properly configured instance returns output showing the efa provider supporting both FI_EP_RDM (Reliable Datagram endpoints, which utilize the hardware SRD protocol and support RDMA operations) and FI_EP_DGRAM (Datagram endpoints):

provider: efa
    fabric: efa
    domain: rdmap0s31-rdm
    version: 121.0
    type: FI_EP_RDM
    protocol: FI_PROTO_EFA
provider: efa
    fabric: efa
    domain: rdmap0s31-dgrm
    version: 121.0
    type: FI_EP_DGRAM
    protocol: FI_PROTO_EFA

Querying EFA Support via AWS CLI

Because AWS continuously expands EFA support to newly released EC2 instance families and sizes, you can dynamically query the exact list of EFA-supported instances in your target AWS Region using the AWS CLI:

aws ec2 describe-instance-types \
    --filters Name=network-info.efa-supported,Values=true \
    --query "InstanceTypes[*].[InstanceType, NetworkInfo.EfaInfo.MaximumEfaInterfaces, NetworkInfo.NetworkPerformance]" \
    --output table

Key Requirements for Enabling OS-Bypass in Production

To ensure your workloads actively use the OS-bypass path rather than falling back to standard TCP over ENA, verify the following configuration requirements:

  • Security Group Rules: An EFA-enabled security group must allow all inbound and outbound traffic (all protocols and ports) to and from itself. Because SRD operates directly over the Nitro fabric outside standard TCP/UDP port numbers, restrictive port rules will block OS-bypass traffic.
  • Placement Groups: Launch instances inside a Cluster Placement Group to minimize physical distance and switch hops between nodes.
  • Memory Locking Limits (ulimit -l): Because OS-bypass pins user-space memory pages for DMA transfers, the operating system must allow locked memory (memlock) to be set to unlimited in /etc/security/limits.conf or container runtime configurations.
  • HugePages and GPUDirect RDMA: On GPU instances (p4d, p5, g5, g6e) and Trainium instances (trn1, trn2), install the aws-ofi-nccl plugin and NVIDIA nvidia-peermem (or Neuron runtime drivers) alongside Libfabric so that EFA can perform GPUDirect RDMA transfers directly between GPU HBM memory and the network card without staging through host system RAM.
