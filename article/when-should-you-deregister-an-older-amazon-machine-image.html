When should you deregister an older Amazon Machine Image?

Deregistering an older Amazon Machine Image in Amazon EC2 should occur when the image is obsolete, contains unpatched security vulnerabilities, or has been superseded by a newer gold image version. Removing unused images prevents accidental launches of outdated software configurations, maintains compliance standards, and helps reduce storage costs when the associated Amazon EBS snapshots are subsequently deleted. Organizations typically execute deregistration after verifying that no active EC2 instances, Auto Scaling launch templates, or disaster recovery plans depend on the legacy image.

Key Scenarios for Deregistering an AMI

Managing the lifecycle of Amazon Machine Images (AMIs) is a critical component of cloud hygiene and infrastructure security. While an AMI itself does not incur a direct catalog listing fee, the underlying storage and operational risks make timely deregistration important.

1. Security Vulnerabilities and Patching Cycles

When a new AMI is baked with updated operating system patches, security agents, or application dependencies, older AMIs immediately become a security liability. If an older AMI remains registered, developers or automated systems might inadvertently use it to provision new EC2 instances, reintroducing patched vulnerabilities (such as CVEs) into your environment. Once the new AMI is validated in production, the superseded image should be deregistered after a brief rollback window.

2. Operating System or Software End-of-Life (EOL)

When an operating system version or embedded software stack reaches its End-of-Life (EOL) or End-of-Support (EOS), vendor security updates cease. Any AMI built on an EOL distribution should be deregistered as soon as workloads are migrated to supported versions to ensure strict adherence to regulatory frameworks like SOC 2, PCI-DSS, or HIPAA.

3. Cost Optimization and Snapshot Cleanup

An EBS-backed AMI consists of metadata pointing to one or more Amazon EBS snapshots. You cannot delete an EBS snapshot while it is associated with a registered AMI. Therefore, if you want to eliminate the monthly storage costs of obsolete snapshots, you must first deregister the AMI and then delete the backing snapshots. If storage cost is \(C\) per gigabyte-month and total obsolete snapshot size is \(S\) gigabytes, removing \(N\) redundant images saves:

\[\text{Monthly Savings} = \sum_{i=1}^{N} S_i \times C\]

Note that due to incremental snapshot behavior in Amazon EBS, deleting an older snapshot only frees up storage blocks that are not referenced by newer snapshots in the same lineage.

4. Golden Image Pipeline Rotation

In automated CI/CD image pipelines (using tools like EC2 Image Builder or HashiCorp Packer), images are frequently generated on a weekly or monthly schedule. Implementing a retention policy—such as keeping only the last \(k\) versions (e.g., \(k = 3\))—prevents catalog clutter and speeds up API queries when describing images in the AWS account.

Pre-Deregistration Checklist

Before deregistering an AMI, verify that removing it will not disrupt automated scaling or recovery workflows. Deregistering an AMI does not affect currently running EC2 instances launched from that AMI, but it prevents new instances from being launched from it.

  1. Check Auto Scaling Groups and Launch Templates: Ensure no active Launch Templates or Launch Configurations reference the AMI ID. If an Auto Scaling group attempts to scale out using a deregistered AMI, the launch activity will fail.
  2. Audit Infrastructure as Code (IaC): Search your Terraform, AWS CloudFormation, or AWS CDK repositories for hardcoded references to the old AMI ID, or verify that SSM Parameters pointing to the latest AMI have been updated.
  3. Verify Running Instances: Identify any long-running EC2 instances still using the AMI. While they will continue running, features that rely on re-launching from the source AMI (such as certain recovery scripts) will break.
  4. Check Cross-Account Shares: If the AMI is shared with other AWS accounts or Organization OUs, confirm that downstream teams have migrated to the newer image version.
  5. Confirm Rollback Window Expiration: Always keep the previous working AMI registered until the newly deployed AMI has proven stable in production for a defined bake period (typically 7 to 30 days).

Deprecation vs. Deregistration

Instead of immediately deregistering an older AMI, AWS allows you to set a deprecation time on the image.

  • Deprecation: Marks the AMI as outdated at a specific date and time. Deprecated AMIs are hidden by default from DescribeImages API calls for users unless explicitly requested, but they still allow existing Launch Templates and Auto Scaling groups to launch instances without failing.
  • Deregistration: Permanently removes the AMI from the EC2 registry. No new instances can be launched from it under any circumstances, and the action cannot be undone.

A common best practice is a two-stage lifecycle: deprecate the AMI immediately when a newer version is released, wait 30 days to monitor for any unexpected dependencies, and then permanently deregister the AMI and delete its associated EBS snapshots.
