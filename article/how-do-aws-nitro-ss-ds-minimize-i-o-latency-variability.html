How Do AWS Nitro SSDs Minimize I/O Latency Variability?

AWS Nitro SSDs minimize I/O latency variability in Amazon EC2 I4i and Im4gn instances by utilizing custom-designed solid-state drive hardware and firmware managed directly by AWS. Unlike off-the-shelf commercial storage drives that rely on unpredictable internal garbage collection cycles and opaque Flash Translation Layer (FTL) operations, Nitro SSDs integrate tightly with the AWS Nitro System. This architecture offloads storage management, encryption, and virtualization tasks to dedicated hardware, reduces tail latency by up to 75 percent compared to previous-generation storage-optimized instances, and ensures predictable, consistent input/output operations per second (IOPS) for latency-sensitive databases and analytics workloads.

The Challenge of Tail Latency in Standard NVMe SSDs

To understand how AWS Nitro SSDs achieve predictable performance, it is first necessary to examine why traditional Non-Volatile Memory Express (NVMe) SSDs experience latency spikes. NAND flash memory cannot be overwritten directly; instead, data must be written to free pages, and stale data must be erased in larger blocks before those pages can be reused.

In standard commercial SSDs, an onboard microcontroller runs a Flash Translation Layer (FTL) that handles logical-to-physical address mapping, wear leveling, and garbage collection. When an SSD is subjected to sustained write workloads, the drive eventually runs low on pre-erased blocks. The FTL must then trigger background garbage collection: reading valid pages from partially full blocks, rewriting them to a new block, and erasing the old block.

When host read requests arrive at the exact moment a NAND die is busy executing a long write or block-erase operation, those read requests are queued behind the ongoing operation. While the average latency (\(\mu\)) of the drive might remain low, the 99th percentile (\(p99\)) and 99.9th percentile (\(p99.9\)) latencies spike dramatically. In distributed databases, a single slow storage node experiencing a garbage collection stall can delay quorum reads or transaction commits across the entire cluster.

Custom Silicon and AWS-Managed Firmware

AWS Nitro SSDs address the root causes of FTL unpredictability by shifting control of the storage medium from generic third-party drive firmware to the AWS Nitro System.

1. Deterministic Garbage Collection and I/O Scheduling

Because AWS designs both the Nitro SSD hardware and its firmware, the storage controller schedules background tasks—such as garbage collection and wear leveling—cooperatively with incoming host I/O traffic. Rather than executing disruptive, monolithic garbage collection passes that block read channels, the firmware breaks maintenance operations into smaller, deterministic intervals and prioritizes latency-sensitive read operations over background writes and erases.

2. Direct Integration with the AWS Nitro System

In EC2 I4i (powered by 3rd generation Intel Xeon Scalable processors) and Im4gn/Is4gen (powered by AWS Graviton2 processors) instances, local NVMe storage is mediated by dedicated Nitro cards. The Nitro System offloads NVMe virtualization, hardware-based AES-256 encryption, and storage routing from the host CPU. Because the host hypervisor is bypassed and the data path goes directly from the instance's virtualized NVMe interface to the Nitro hardware, software-induced jitter and context-switching overhead are virtually eliminated.

3. Provisoned Over-Provisioning and Isolation

Sustained write performance degrades rapidly when a drive approaches full capacity due to write amplification. Write Amplification Factor (\(\text{WAF}\)) is defined as:

\[\text{WAF} = \frac{\text{Bytes Written to Flash Media}}{\text{Bytes Written by Host}}\]

Nitro SSDs maintain dedicated over-provisioned NAND capacity and utilize stream-aware placement algorithms that keep \(\text{WAF}\) low even under sustained random write workloads. In multi-tenant configurations where a physical Nitro SSD is partitioned across smaller instance sizes (such as i4i.large or im4gn.xlarge), the Nitro controller enforces strict hardware-level quality of service (QoS) and physical channel isolation so that noisy-neighbor workloads cannot induce latency variability in adjacent instances.

4. Rapid Firmware Updates Without Instance Reboot

Traditional SSD firmware updates require draining and rebooting the underlying physical host, making rapid performance tuning difficult in cloud environments. AWS designed Nitro SSDs so their firmware can be updated rapidly and non-disruptively via the Nitro control plane, allowing continuous optimization of I/O scheduling algorithms across the fleet.

Performance Impact on EC2 I4i and Im4gn Instances

Compared to third-generation storage-optimized instances (I3 and I3en), EC2 I4i and Im4gn instances equipped with AWS Nitro SSDs deliver two primary measurable improvements:

  • Up to 60% Lower Average I/O Latency: Streamlined data paths and optimized NAND channel management reduce the baseline latency for read and write operations.
  • Up to 75% Lower I/O Latency Variability: The variance (\(\sigma^2\)) and high-percentile tail latencies (\(p99\) and \(p99.9\)) during mixed read/write workloads are significantly compressed, preventing throughput drops during heavy compaction or checkpointing phases.

OS and Application Best Practices for Minimizing Latency Variability

While Nitro SSDs handle hardware-level determinism, guest operating system and application configurations inside I4i and Im4gn instances play a crucial role in preserving low latency variability from end to end.

Configure the Linux I/O Scheduler

For local NVMe drives backed by Nitro SSDs, complex OS-level I/O sorting adds unnecessary CPU overhead and latency. Set the Linux block device I/O scheduler to none (or noop on older kernels) so that requests pass directly to the multi-queue NVMe driver (nvme-mq):

echo none | sudo tee /sys/block/nvme1n1/queue/scheduler

Enable Periodic TRIM / Discard Operations

To help the Nitro SSD firmware maintain optimal free-block pools and minimize write amplification, ensure the filesystem informs the underlying storage when blocks are no longer in use. Instead of mounting filesystems with the discard option—which sends synchronous discard commands during file deletion and can introduce latency jitter—use a periodic fstrim cron job or systemd timer (fstrim.timer) alongside XFS or ext4 filesystems.

Use Torn-Write Protection for Databases

AWS Nitro SSDs on I4i instances support 16 KB atomic writes (torn-write protection). Relational databases like MySQL (InnoDB) normally use a doublewrite buffer to protect against partial page writes during a power failure or crash, effectively doubling write I/O bandwidth requirements. By aligning filesystem block sizes and configuring the database to leverage Nitro SSD torn-write protection, you can disable the doublewrite buffer, reducing write pressure on the SSD and further stabilizing \(p99\) read and write latencies.

Poll queues and IRQ Affinity

For extreme low-latency workloads (such as ScyllaDB, Aerospike, or Apache Cassandra), ensure that NVMe interrupt requests (IRQs) are balanced across vCPUs or use kernel-bypass/polling mechanisms (such as io_uring with IORING_SETUP_IOPOLL or SPDK) to eliminate interrupt wakeup latency.
