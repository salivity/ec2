When Should You Avoid Storing Databases on EC2 Instance Store?

Engineers should avoid storing primary, unbacked database records on an Amazon EC2 instance store volume whenever data durability and persistence across instance lifecycle events are required. Because EC2 instance store provides temporary block-level storage physically attached to the host computer, any data stored on these volumes is permanently lost if the underlying hardware fails, the instance is stopped, or the instance is terminated. Consequently, primary database records that are not actively replicated to a durable storage layer or secondary cluster nodes must never reside exclusively on instance store volumes.

Understanding Amazon EC2 Instance Store Architecture

An Amazon EC2 instance store consists of one or more physical NVMe or SSD disks attached directly to the physical server hosting your virtual machine. Because the storage resides on the same physical host, it bypasses the network layer required by network-attached storage systems like Amazon Elastic Block Store (EBS). This direct attachment delivers ultra-low latency and high random I/O operations per second (IOPS).

However, this architectural advantage comes with a strict lifecycle trade-off: the storage is tied entirely to the running state of the specific EC2 instance on that specific physical host. Unlike Amazon EBS, which replicates data within an Availability Zone independently of the compute instance lifecycle, an instance store volume has no built-in redundancy or detachment capability.

Core Scenarios Where Instance Store Must Be Avoided

1. Single-Node Primary Databases Without Replication

If a database architecture relies on a single primary node without synchronous or near-real-time asynchronous replication to standby instances, storing its primary data directory on an instance store volume introduces an unacceptable risk of total data loss.

In a standalone database setup, the probability of data survival \(P(\text{survival})\) over time \(t\) depends entirely on both the hardware reliability and operational stability of the single host:

\[P(\text{survival}) = 1 - P(\text{host failure or stop event})\]

If the database lacks external replication or continuous transaction log shipping to durable storage like Amazon S3 or Amazon EBS, any host degradation results in immediate, unrecoverable loss of all committed transactions since the last external backup.

2. Workloads Requiring Stop and Start Lifecycle Operations

Engineers frequently stop and restart EC2 instances to resize instance types, apply maintenance updates, or reduce compute costs during off-peak hours. When an EC2 instance is stopped, AWS deallocates the virtual machine from the physical host. When the instance is started again, it is typically provisioned on a completely different physical server.

While data on an instance store volume persists through a standard operating system reboot, stopping or hibernating an instance triggers a permanent wipe of the instance store disks. Any primary database records stored on those volumes vanish the moment the instance transitions to the stopped state.

3. Compliance and Zero-RPO Requirements

Financial, healthcare, and transactional systems often mandate a Recovery Point Objective (RPO) of zero:

\[\text{RPO} = 0\]

An RPO of zero means the system cannot tolerate losing a single committed transaction. Even if a database on an instance store performs periodic snapshots to Amazon S3 every 15 minutes, any failure of the underlying physical drive or host hypervisor results in up to 15 minutes of lost transactional records. Without synchronous replication to durable volumes or multi-node quorum writes across separate Availability Zones, an instance store cannot satisfy strict durability or compliance standards.

4. Lack of Automated Volume Snapshot Capabilities

Amazon EBS allows engineers to create point-in-time snapshots directly via AWS APIs and lifecycle policies without interrupting the underlying file system. EC2 instance store volumes do not support native AWS snapshot APIs. Backing up a primary database running on an instance store requires custom, database-aware tooling that reads data from the file system, compresses it, and streams it over the network to Amazon S3 or Amazon EFS, consuming both CPU cycles and network bandwidth on the host.

Events That Trigger Permanent Data Loss on Instance Store

Understanding the exact conditions that destroy data on an instance store volume clarifies why uninhibited primary records are vulnerable:

Lifecycle Event Instance Store Data Retained? Amazon EBS Data Retained?
Operating System Reboot Yes Yes
Instance Stop No (Erased) Yes
Instance Termination No (Erased) Configurable (DeleteOnTermination)
Underlying Hardware Drive Failure No (Erased) Yes (Replicated within AZ)
Instance Type Resize No (Requires Stop/Start) Yes

Valid Database Use Cases for EC2 Instance Store

While primary, uninhibited database records should never rely solely on instance store volumes, database engineers regularly use instance store for specific, ephemeral, or distributed database functions:

  • Temporary Tablespaces and Sort Files: Relational databases such as PostgreSQL, MySQL, and Oracle frequently write large temporary tables, hash joins, and sort operations to disk when queries exceed available RAM. Placing the temp_tablespaces or tmpdir directory on an NVMe instance store accelerates query execution without risking primary data integrity.
  • Buffer Pool Extensions and Caching: Database engines that support L2 flash caching can use instance store disks to extend memory capacity at a fraction of the cost of RAM.
  • Distributed NoSQL Databases with Built-In Quorum: Databases like Apache Cassandra, ScyllaDB, or OpenSearch are specifically architected for shared-nothing local storage. When configured with a replication factor \(RF \ge 3\) across multiple Availability Zones, the loss of a single node's instance store is automatically healed by streaming data from surviving replica nodes.

Recommended Alternatives for Primary Database Storage

When designing storage for a primary database on AWS where data durability is mandatory, engineers should select from the following architectures:

  1. Amazon EBS GP3 or IO2 Block Express: For self-managed databases on EC2, store the primary data directory and write-ahead logs (WAL) on Amazon EBS volumes. Use io2 Block Express when sub-millisecond latency and high durability (\(99.999\%\)) are required for mission-critical workloads.
  2. Hybrid Storage Layout on EC2: Mount an Amazon EBS volume for primary data files, indexes, and transaction logs while mounting the local NVMe instance store exclusively for temporary sort files, swap space, and local read caches.
  3. Managed Database Services: Offload storage durability entirely by using Amazon RDS or Amazon Aurora, which automatically replicate storage across three Availability Zones using a distributed quorum architecture.
